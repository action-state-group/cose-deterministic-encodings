                    Deterministic Encodings for COSE
           draft-mih-sokolov-cose-deterministic-encodings-03

Abstract

   A COSE Hash Envelope signs the digest of a preimage, not the preimage
   itself.  When the preimage is the encoding of a structured value,
   such as a CBOR data item, and a verifier holds that value but not the
   bytes that were hashed, the verifier has to encode the value again,
   and the digest matches only if it applies the same deterministic
   encoding as the producer.  CBOR permits more than one encoding of the
   same data item, and the preimage content type does not identify the
   encoding that was applied.  This document defines a COSE Hash
   Envelope protected-header parameter that identifies the encoding: the
   integer 1 for the Core Deterministic Encoding Requirements of RFC
   8949, or a URL for any other encoding, named by the application
   profile that uses the parameter.  A verifier ignores a value that
   does not identify an encoding it implements.

1.  Introduction

   The COSE Hash Envelope [RFC9995] signs the digest of a preimage and
   identifies the hash algorithm (258), the content type of the preimage
   (259), and optionally where the preimage can be retrieved (260).  A
   verifier that holds the preimage can check that the digest of it,
   produced with the hash algorithm identified by payload-hash-alg
   (258), matches the payload, as [RFC9995] Section 5.3 describes.  That
   check needs no information from this document, and retaining the
   preimage is the simplest way to make it possible.

   The Hash Envelope carries the digest, not the preimage, and payload-
   location (260) is optional.  The content therefore reaches a
   verifier, if at all, from outside the Hash Envelope, in whatever form
   its application provides, which can be a structured value rather than
   the bytes that were hashed.  The content can arrive as a data item
   inside a larger CBOR message, and unless the message wraps that item
   in a byte string, most CBOR decoders cannot return its encoded bytes
   ([I-D.ietf-cbor-serialization] Appendices H.1 and J.1).  A system can
   also store the content in another representation -- for example, a
   software inventory that keeps Concise Software Identification
   (CoSWID) tags [RFC9393] as records in a database -- rather than keep
   a second copy of each item as the bytes that were hashed, provided
   that representation preserves each data item exactly (Section 6).  To
   check such content against its Hash Envelope, the verifier has to
   encode the value again, the case in which
   [I-D.ietf-cbor-serialization] Section 5.3.1 says deterministic
   encoding becomes necessary and notes that designs of this kind are
   often chosen to reduce data size, preserve privacy, or meet other
   design constraints.  COSE meets the same need for its own
   Sig_structure, which the signer and the verifier each construct
   rather than transmit, by fixing how that structure is encoded
   ([RFC9052] Sections 4.4 and 9).  For a Hash Envelope preimage, whose
   content type the application chooses, COSE fixes no encoding.

   Re-encoding reproduces the preimage only if the verifier applies the
   encoding the producer applied.  CBOR permits more than one encoding
   of the same data item ([RFC8949] Section 4.2), and a producer need
   not apply a deterministic one: {"x": 1.5} is a1 61 78 f9 3e 00 under
   the Core Deterministic Encoding Requirements ([RFC8949]
   Section 4.2.1) and a1 61 78 fb 3f f8 00 00 00 00 00 00 when every
   floating-point value is written as binary64, and both are valid CBOR.
   The preimage-content-type (259) names the type of the content, such
   as application/swid+cbor, not the encoding applied to it.  A verifier
   that assumes an encoding the producer did not state cannot tell a
   modified value from one encoded another way.  The parameter lets the
   verifier tell the two apart: when the producer states the encoding, a
   mismatch means the value the verifier holds is not the value the

   producer encoded.  When it does not, nothing changes: the verifier
   checks the content binding as [RFC9995] Section 5.3 describes
   (Section 4.3).

   This document defines one protected-header parameter, deterministic-
   encodings, which identifies that encoding: the integer 1 identifies
   the Core Deterministic Encoding Requirements of [RFC8949]
   Section 4.2.1 (Section 3.1), and any other encoding is identified by
   a URL that an application profile names (Section 3).  This document
   defines no encoding of its own.  As with the hash algorithm in
   payload-hash-alg (258), the producer states its choice and the
   verifier follows it.  Naming a canonicalization or a profile by a URI
   has precedent: XML Signature names the canonicalization algorithm
   applied to the signed content by a URI ([RFC3275] Section 6.1), and
   the eat_profile claim names a profile, including the encoding choices
   it fixes, by a URI or an OID ([RFC9711] Sections 4.3.2 and 6.4).  The
   parameter uses the extension point the Hash Envelope protected header
   already provides (Section 4 of [RFC9995]: * (int / tstr) => any).
   The encoding is not carried as a media-type parameter of preimage-
   content-type (259).  The application/cbor media type defines no
   parameters ([RFC8949] Section 9.3), so such a parameter would have to
   be registered for every media type the encoding applies to, and a
   CoAP Content-Format number carries only the parameters fixed in its
   registry entry ([RFC7252] Section 12.3), so each pairing of media
   type and encoding would also need its own number.  A profile that has
   its own media type, such as application/vnd.ipld.dag-cbor [DAG-CBOR],
   is already identified by 259; content labelled application/cbor, or
   with an application's own type such as application/swid+cbor, is not.

   The scope of this document is structured values, such as CBOR data
   items, and the deterministic encodings that serialize them.  Media
   encodings, such as those of images, and builds of software from
   source code are out of scope; such content is checked from its bytes,
   as [RFC9995] Section 5.3 describes.

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   "COSE", "COSE_Sign1", and "protected header" are defined in
   [RFC9052]; "CDDL" in [RFC8610]; "Hash Envelope" and "preimage" in
   [RFC9995].  As in [RFC9995], the payload of a Hash Envelope is a
   digest, and the preimage consists of the bytes that were hashed to
   produce it.  The Hash Envelope labels this document builds on are 258
   (payload-hash-alg), 259 (preimage-content-type), and 260 (payload-
   location).

   This document also uses the following terms:

   Structured value:  A value with internal structure, such as a CBOR
      data item, that a deterministic encoding serializes to create a
      preimage.

   Application profile:  A specification of an application or protocol
      that uses deterministic-encodings and states which encodings its
      producers apply and its verifiers implement: the one this document
      identifies by the integer 1, or others, each named by a URL.

   Content binding:  The correspondence between content a verifier holds
      -- a preimage, or a structured value -- and the payload of a Hash
      Envelope.  A verifier checks it as [RFC9995] Section 5.3
      describes.  The check succeeds when the digest of the preimage,
      held or re-created from a structured value, produced with the hash
      algorithm identified by payload-hash-alg (258), matches the
      payload, and the verifier found no inconsistency in the protected
      header (Section 4.2); otherwise it fails.  This document adds no
      other outcome.

3.  The deterministic-encodings Header Parameter

   TBD_1:  deterministic-encodings.  The deterministic encoding with
      which a structured value was serialized to create the bytes that
      were hashed (preimage) to produce the payload, given as the
      integer 1 or as a URL.

   It extends [RFC9995] by adding one optional member to the
   Hash_Envelope_Protected_Header CDDL of [RFC9995] Section 4, alongside
   the members for labels 258-260.  The extended rule restates the
   [RFC9995] rule with that member added:











Mih & Sokolov              Expires 27 May 2027                  [Page 5]

Internet-Draft        COSE Deterministic Encodings         November 2026


   Hash_Envelope_Protected_Header_With_Encoding = {
       ? &(alg: 1) => int,
       &(payload_hash_alg: 258) => int,
       ? &(payload_preimage_content_type: 259) => uint / tstr,
       ? &(payload_location: 260) => tstr,
       ? &(deterministic_encodings: TBD_1) => 1 / tstr,
       * (int / tstr) => any
   }

   Label TBD_1 MAY be present in the protected header and MUST NOT be
   present in the unprotected header, following the placement rule
   [RFC9995] states for labels 258 through 260.  When label TBD_1 is
   present, preimage-content-type (259) MUST also be present
   (Section 4.2).  A producer MUST NOT list label TBD_1 in the crit
   header parameter ([RFC9052] Section 3.1), so that a verifier that
   implements only [RFC9995] can ignore it.

   The value of deterministic-encodings is either the unsigned integer 1
   or a text string holding a URL.  The integer 1 identifies the Core
   Deterministic Encoding Requirements of [RFC8949] Section 4.2.1
   (Section 3.1).  This document defines no other integer value and
   creates no registry.

   A text string value is a URL: a URI ([RFC3986] Section 3) with the
   "https" scheme ([RFC9110] Section 4.2.2) that links to the part of a
   specification that defines exactly one deterministic encoding.  When
   the linked document defines more than one encoding, the URL MUST
   carry a fragment ([RFC9110] Section 4.2.5) that selects the section
   defining the encoding that was applied.  A producer copies the URL of
   the encoding it applied.  A verifier compares the value with the URLs
   of the encodings it implements, character by character ([RFC3986]
   Section 6.2.1), and does not dereference it.

   Which URLs a producer can use, and which a verifier acts on, is
   decided by the application profile that uses this parameter, not by
   this document; a profile that names a URL is responsible for the URL,
   the encoding, and the encoding's Applicable Content Types
   (Section 4.2).  No registry of these URLs is needed, and a value that
   a verifier does not implement changes no verification outcome: the
   verifier ignores it (Section 4.3).

3.1.  The Value for CBOR Content

   For CBOR content, this document defines one value: the integer 1.  As
   the value of deterministic-encodings, 1 states that the structured
   value was encoded according to the Core Deterministic Encoding
   Requirements of [RFC8949] Section 4.2.1.  It does not stand for the
   other encodings that [RFC8949] describes, such as the length-first
   map key ordering of its Section 4.2.3.  For a CBOR sequence
   [RFC8742], each data item is encoded according to these requirements.
   The choices that [RFC8949] Section 4.2.2 leaves to a protocol,
   including the representation of NaN values, are not part of this
   encoding (Section 6).

   A producer that applied this encoding and includes deterministic-
   encodings MUST set it to the integer 1, not to a URL, so that
   producers and verifiers use one value for the encoding.  The integer
   takes 1 byte; the URL of that section on the RFC Editor's site would
   take 59 bytes.

   An RFC does not change once it is published, so the integer 1 names
   one fixed text.  A later specification that changes deterministic
   encoding is identified by a URL of its own (Section 3), and Hash
   Envelopes that carry the integer 1 keep their meaning.  For example,
   [I-D.ietf-cbor-serialization] defines preferred-plus serialization
   (its Section 4) and deterministic serialization (its Section 5), and
   its deterministic serialization excludes NaNs other than 0xf97e00.
   Once published as an RFC, its deterministic serialization could be
   identified by the URL of the section of that RFC that defines it,
   with the fragment.  Its preferred-plus serialization is not
   deterministic when the value contains a map (its Section 5.3.2), so
   it is not an encoding for this parameter.

   Other encodings, of CBOR or of other content such as JSON, are
   identified by URLs that the application profiles that use them name
   (Section 3); this document does not list them.  A URL is not the
   integer 1, even when it links to Section 4.2.1 of [RFC8949]: a
   verifier compares a URL only with the URLs of the encodings it
   implements.

4.  Producer and Verifier Behavior

Internet-Draft        COSE Deterministic Encodings         November 2026


4.1.  Producers

   When a producer creates the preimage by applying a deterministic
   encoding to a structured value, it SHOULD include deterministic-
   encodings, so that a verifier holding only the structured value can
   re-create the preimage.  When present, the value MUST identify the
   encoding actually applied.  A producer that serializes a structured
   value without a deterministic encoding, or whose preimage is not the
   serialization of a structured value -- for example application/octet-
   stream content, an image, or an archive -- has no encoding to
   identify, and the parameter is absent; the content binding can then
   be checked only from the preimage bytes.

4.2.  Consistency with preimage-content-type

   The Applicable Content Types of the encoding that the integer 1
   identifies (Section 3.1) are application/cbor, application/cbor-seq,
   application/cose, application/cose-key, application/cose-key-set,
   application/cose-x509, application/cwt, and application/multipart-
   core, and media types with the +cbor, +cbor-seq, +cose, +cwt, or +sd-
   cwt structured syntax suffix.  When deterministic-encodings is
   present, preimage-content-type (259) MUST also be present, and its
   value MUST match one of the Applicable Content Types of the encoding
   that deterministic-encodings identifies:

   *  A 259 value that is a media-type name matches when its type and
      subtype -- with any parameters removed, and compared case-
      insensitively ([RFC6838] Section 4.2) -- equal a listed media
      type, or when its subtype ends in a listed structured syntax
      suffix ([RFC6838] Section 4.2.8).

   *  A 259 value that is a Content-Format number matches when the CoAP
      Content-Formats registry ([RFC7252] Section 12.3) assigns that
      number to a matching media type with no content coding.

   A producer MUST NOT emit a Hash Envelope that violates these rules --
   for example, one pairing the integer 1 with application/json.  A
   verifier that implements the encoding that deterministic-encodings
   identifies, and finds preimage-content-type (259) absent or with a
   value that does not match the Applicable Content Types of that
   encoding, MUST treat the check of the content binding as failed,
   without attempting recomputation.  This check comes first, and takes
   precedence over Section 4.3.  A verifier that does not implement the
   identified encoding, like one that implements only [RFC9995], ignores
   the parameter, and its results are unchanged.

4.3.  Verifying the Content Binding

   A verifier that holds the preimage itself -- for example, as
   retrieved from payload-location (260) -- checks the content binding
   as [RFC9995] Section 5.3 describes: it checks whether the digest of
   the preimage, produced with the hash algorithm identified by payload-
   hash-alg (258), matches the payload.  That check needs no encoding
   information, and applies whether or not deterministic-encodings is
   present, subject to Section 4.2.

   A verifier that holds only a structured value -- for example, content
   it received, stored, or decoded in a form other than the preimage
   itself -- has to re-create the preimage by encoding that value.  When
   deterministic-encodings identifies an encoding the verifier
   implements, the verifier MUST encode the value with that encoding,
   and MUST NOT infer the encoding from preimage-content-type (259) or
   from the structure of the value.  If the digest of the result does
   not match the payload, the check fails.  It also fails if the
   verifier cannot produce that encoding of the value -- for example,
   when the value holds a NaN with a payload that its encoder does not
   support (Section 3.1).

   When deterministic-encodings is absent, or its value does not
   identify an encoding the verifier implements -- for example, a URL
   that the verifier's application profile does not name, an integer
   other than 1, or a value of another type, such as the floating-point
   number 1.0 -- the verifier ignores the parameter, and checks the
   content binding as it would for a Hash Envelope without it, as
   [RFC9995] Section 5.3 describes.  A verifier that holds no preimage
   then has nothing to hash, and the check fails.  This document adds no
   other outcome.

   A Hash Envelope produced without this parameter -- including any
   produced before the parameter was registered -- is not defective: its
   content binding can still be verified from the preimage bytes.
   Signature validity is unaffected by the check of the content binding:
   a verifier that has not established the content binding can still
   validate the signature of the COSE_Sign1 as specified in [RFC9052].

   These use Extended Diagnostic Notation ([RFC8610] Appendix G), in the
   style of [RFC9995] Section 4.1; signature and key material are
   truncated.

   The structured value {"b": 2, "a": 1}, a CBOR map, encoded per the
   Core Deterministic Encoding Requirements of [RFC8949] Section 4.2.1
   (bytewise key order, placing "a" before "b"), gives the 7-octet
   preimage a2616101616202, whose SHA-256 digest is
   a0d3af9e86e5517f729bad0657e2c6f3b7d03899894c8d6b33759074c893b5e3:

   18([ # COSE_Sign1
     <<{
       / alg                     / 1: -7, # ES256
       / hash algorithm          / 258: -16, # sha-256
       / preimage type           / 259: "application/cbor",
       / deterministic encodings / TBD_1: 1, # RFC 8949, Section 4.2.1
     }>>
     / unprotected / {},
     / payload     / h'a0d3af9e...c893b5e3', # digest above
     / signature   / h'...'  # 64 octets, r || s
   ])

   [RFC9393] registers application/swid+cbor for Concise Software
   Identification (CoSWID) tags but does not require a deterministic
   encoding of them, so two producers may serialize the same tag as
   different byte sequences.  A producer that applies the Core
   Deterministic Encoding Requirements before hashing a CoSWID tag sets
   preimage-content-type (259) to application/swid+cbor and
   deterministic-encodings to the integer 1 (Section 3.1) -- recording
   its own choice, not a CoSWID requirement -- so that a verifier
   holding the decoded tag knows how to re-create the preimage.

   A Hash Envelope over JSON content can carry deterministic-encodings
   with the URL of a specification that defines a deterministic encoding
   of JSON, such as "https://json-spec.example/deterministic", with
   preimage-content-type "application/json", when the application
   profile the producer follows names that URL.  This document does not
   name it.  A verifier that implements that encoding and holds the
   decoded JSON value re-creates the preimage with it.  A verifier that
   does not implement it ignores the parameter, and checks the content
   binding as [RFC9995] Section 5.3 describes (Section 4.3).

6.  Security Considerations

   A deterministic encoding fixes the preimage for a given structured
   value, so decoding a preimage and encoding the result again
   reproduces the preimage only if decoding preserved that value
   exactly.  Decoding into a programming language's native types can
   lose distinctions the encoding depends on -- for example, between
   integer and floating-point numbers, or the presence of a tag.
   Choices that decide which data item represents a value, such as those
   [RFC8949] Section 4.2.2 leaves to each protocol for tags and for



Mih & Sokolov              Expires 27 May 2027                 [Page 10]

Internet-Draft        COSE Deterministic Encodings         November 2026


   integer versus floating-point values, belong to the structured value,
   not to the encoding that deterministic-encodings identifies.  A
   choice that changes only how the same data item is serialized, such
   as encoding every floating-point value as binary64, is a different
   encoding, not the one that the integer 1 identifies (Section 3.1).  A
   producer that re-reads stored content before hashing MUST ensure the
   preimage it hashes is byte-identical to the encoding's own output.  A
   verifier that re-creates a preimage from a structured value
   (Section 4.3) needs that value exactly as the producer encoded it;
   otherwise its recomputed digest can differ from the payload, and the
   check of the content binding then fails.

   A verifier does not dereference a URL in deterministic-encodings, so
   the value causes no network access, and a URL whose resource has
   moved or changed does not change the verifier's result.  A value that
   does not identify an encoding the verifier implements has no effect
   on the result (Section 4.3).

7.  Privacy Considerations

   A digest over deterministically encoded content is a stable function
   of that content, so the payload is linkable wherever the content
   recurs.  If the structured value comes from a low-entropy space,
   encoding and hashing candidate values can recover it; this risk
   already exists wherever [RFC9995] is used, and identifying the
   encoding removes an ambiguity that might have slowed such an attempt.

Appendix A.  Changes from Version 02

   This section is to be removed before publishing as an RFC.

   *  The value of deterministic-encodings is the integer 1 or a URL
      (Section 3).  The integer 1 identifies the Core Deterministic
      Encoding Requirements of [RFC8949] Section 4.2.1, which version 02
      identified by the URL of that section; the integer takes 1 byte,
      the URL 59.  Any other encoding is still identified by a URL that
      an application profile names.  This document creates no registry
      and defines no other integer value.

   *  A producer that applied the Core Deterministic Encoding
      Requirements sets the parameter to the integer 1, not to a URL
      (Section 3.1).  A verifier of this version ignores the URL that
      version 02 listed (Section 3.1, Section 4.3).  Version 00 used the
      integer 1 for the same encoding, through a registry that version
      01 removed.

   *  A verifier also ignores an integer other than 1 and a value of
      another type, such as the floating-point number 1.0 (Section 4.3).
      The example in Section 5 carries the integer 1.

   *  Editorial: the fragment rule cites [RFC9110] Section 4.2.5; the
      text no longer predicts a section number of
      [I-D.ietf-cbor-serialization] once it is an RFC; the eat_profile
      precedent names a profile by a URI or an OID (Section 1).

Appendix B.  Changes from Version 01

   This section is to be removed before publishing as an RFC.

   *  The value of deterministic-encodings became a URL, not a token: an
      "https" URL that links to the section of a specification that
      defines the encoding (Section 3).  Version 01 used the text string
      "dtrm", the name [I-D.ietf-cbor-serialization] gives to
      deterministic serialization in its CDDL control operator.  A URL
      needs no registry: the application profile that names a URL is
      responsible for it.

   *  Version 02 listed one URL, for CBOR content: the URL of
      Section 4.2.1 of [RFC8949], the Core Deterministic Encoding
      Requirements, with its fragment.  A URL for a document that
      defines more than one encoding, such as [RFC8949] or
      [I-D.ietf-cbor-serialization], carries a section fragment
      (Section 3).  An RFC does not change, so the URL needs no
      replacement later.  Unlike "dtrm", this encoding does not exclude
      NaNs other than 0xf97e00: the representation of NaN values is one
      of the choices that [RFC8949] Section 4.2.2 leaves to a protocol.

   *  Other URLs are named by the application profiles that use the
      parameter, not by this document (Section 2, Section 3).  A
      verifier ignores a URL it does not implement, so an arbitrary URL
      changes no verification outcome.

   *  The outcome "unverified" is removed: the check of a content
      binding succeeds or fails, as [RFC9995] Section 5.3 describes it.
      A verifier of version 02 ignored deterministic-encodings when it
      was absent or its value was not the URL of an encoding the
      verifier implemented, including the text string "dtrm", and
      checked the content binding as for a Hash Envelope without it.
      When a verifier cannot produce the identified encoding of a
      structured value, the check fails.  Only a verifier that
      implements the identified encoding checks preimage-content-type
      (259) against it (Section 4.2, Section 4.3).

   *  Examples showed the URL and a JSON case with a URL that this
      document does not list (Section 5); Security Considerations state
      that the URL is not dereferenced (Section 6).

   *  The abstract and the introduction no longer rest on RFC 8949
      describing more than one deterministic encoding.  The introduction
      shows instead a value that has two valid CBOR encodings, one of
      them deterministic, and why stating the encoding lets a verifier
      tell a modified value from one encoded another way (Section 1).
